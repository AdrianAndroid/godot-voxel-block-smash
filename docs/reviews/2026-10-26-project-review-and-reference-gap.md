## 1. 结论与证据边界

项目已经具备“加载体素模型 → 五列炮台队列 → 点击列首入槽 → 同色可达选靶 → 真实飞行和碰撞 → 消除、扣弹与返还 → 连击和结算”的核心实现。它不是空工程，但也还不能据此宣布参考图所呈现的完整游玩体验已经实现。

最显著的差距依次是：后排队列信息不可见、部分操作入口缺失、消除反馈偏弱、模型造型与材质层次不足，以及完整青蛙的实机通关与生命周期验证尚未闭环。应先修状态和存档边界，再完善玩家能看懂、能操作的界面，最后优化视觉和节奏。

证据分三类：

- **源码确认**：存在实际实现且能追踪到调用链，不等于本次运行通过。
- **历史记录**：`reports/android/cq/cq-acceptance.md`、`docs/dev-step-log.md` 中的已有结果，本次未重跑。读取时 CQ-T01～T09 为桌面 PASS，CQ-T10～T16 仍为 NOT_RUN。
- **截图观察**：用户提供三张示例游戏截图，不是本项目截图。能判断布局、造型、同屏效果；不能由静态截图确定发射间隔、命中算法、道具语义、完整失败条件或帧率。

本文按 `docs/tasks/cannon-queue-redesign.md` 的新规则审查，不把旧版异色反弹、多次消除与新实现的差异误判为缺陷。后续 S07/S08/S09 未完成功能与已经存在的代码问题分列。历史文档里的执行授权不能代替本轮用户授权，本文不执行任何修复。

## 4. 现有实现与参考图的具体差距

### 4.1 最大的交互差距：看不到后排，无法规划

参考图每列至少可看到约三门炮，玩家能观察下一门颜色与弹量；本项目只有五个列首视图和深度数字。即使队列数据正确，玩家仍无法判断“先用哪列，才能露出想要的颜色”。这影响策略可读性，不只是装饰。

建议每列显示前三门，首排全亮可点，后两排可见但不能上位，深处使用遮罩和剩余数量；增加纵向浏览且始终保持逻辑列首身份。点击确认数据迁移后，播放约 0.18s 上位、0.15s 补位，动画中用稳定 turret_id 关联对象。移动超过约 12 个逻辑像素应判滚动而非点击。验收必须覆盖长列、短列、空列、满槽、多次快速点击、滚动后误触。

### 4.2 青蛙数量相近，轮廓、剥层内容和材质仍不同

参考图眼睛大、头部宽、腹部和四肢区分明确；每块都有亮边、暗面和细缝，斜视时能读出体积。现有 `reports/desktop/cq/frog_02_front.png` 是离线正交预览，能看到眼睛、腹部和脚部，但不能代表 Godot 最终画面。它提示造型还需检查脸部层次、嘴部比例及手脚轮廓。

源码材质是硬边 BoxMesh、roughness=0.9、无方向光阴影，背景为深灰；与参考图的紫灰背景、积木亮边和丰富明暗有明确配置差异。建议先用自有低面数倒角共享网格或轻量边缘明暗方案，保持单 MultiMesh；调主光/环境光让正面、顶面、侧面有区分，再考虑接触阴影。不能用每体素一个 Node 或碰撞体换质感。

模型当前实际只有六色且绿色占 77.1%，而图 3 剥层后出现多种内部色。优化应设计“外层可读轮廓—中层色带—内部目标”的分布，让旋转后出现新的可达选择；不是随机往内部撒色块。每次改模型须重算分色弹量、更新 revision/hash、重跑可解性验证，旧存档应拒绝套用。无需追求恰好 4577 块。

### 4.3 射击有逻辑，视觉连续性不足

参考图通过高亮弹珠、拖尾和多个命中点构成连续动作。本项目有同色球和炮口闪光，但没有长拖尾；每炮最多一颗在途，射速受飞行时间限制。不能直接根据参考图就解除在途限制，这会改变预订与返还设计。

先记录真实飞行时长、每炮成功发射间隔、等待目标占比、超时返还比率，确认慢来自路程、搜索还是节流，再在现规则下调 ball_speed。视觉层先加有限长度的淡出拖尾、亮芯，保持颜色身份可辨，禁止靠假球或直接删块制造热闹。

### 4.4 命中反馈存在可量化的尺寸问题

`HitEffects._box()` 的边长为 0.08，粒子缩放再乘 0.05～0.12，最终只有 **0.004～0.0096 个世界单位**；当前 voxel_size=1，即体素边长的 **0.4%～0.96%**。参考图碎块明显可见，现实现即使事件触发正确，投影后仍很容易看不见。

建议最终碎块边长以体素为基准取 0.08～0.18 的候选范围，例如 mesh=0.13，再乘约 0.62～1.38；在真机视距下调节。补一层面向相机的短寿命同色光圈，最多持续约 0.3～0.5s；保持原有 512 总粒子和 0.8s 寿命上限。粒子预算与光圈预算分开计数，优先池化。

连击建议采用模型区域右上的稳定锚点，数字做短促弹跳，避免每次命中都在不同位置生成大文字遮住目标；命中点可保留更轻的局部反馈。连击不应挤占顶部剩余计数。

### 4.5 UI 信息层级与操作完整度不足

参考图有清晰的关卡标识、剩余数量图标、五个圆槽、整齐队列和四个道具图标。当前主要是文本标签、炮台底座及文字道具按钮，空槽显示“空”、锁槽显示“锁”，缺少统一的视觉语言。

建议保留现有区域划分作为起点：顶部约 0～10%、模型约 10～56%、槽位约 57～65%、队列约 66～91%、底部约 92～100%。这是项目的设计起点，不是从参考图精确量出的比例；实际需按安全区和真机调整。空槽使用统一圆形凹槽，锁槽加锁图标；四道具采用自有图标、名称、独立次数角标。取回/合成作为次级操作，避免与四道具挤成同一条拥挤按钮行。

补运行中的暂停菜单：继续、重开、返回列表、音效开关。当前重开/返回只在结算遮罩出现，无目标时玩家缺少及时退出或重开的入口。约 5s 无进展提示“旋转模型或取回炮台”，提示不能误判失败或强制操作。

### 4.6 功能入口不能用服务代码代替

合成服务已经存在，但 HUD 点击列首只执行上位；需要显式合成模式，显示第一门选择状态、允许的同色第二门及合成后弹量，超 160 解释失败且不修改。

“任意指”应按本项目新规则实现同色、可达、未预订目标的优先锁定；选中目标加轮廓/标记，目标失效后恢复普通选靶并提示。不得恢复旧异色万能弹逻辑。尚未接通时应禁用并说明，而非消耗库存后永远待发。

## 5. 代码与逻辑问题清单

以下行号是审查时定位，Claude 后续修改可能使其移动；复核以文件和函数名为准。P1 表示优先修复，P2 表示正常优先级。均为静态路径确认或明确代码推导，本次没有新增运行复现证据。

### R01 / P1：最后一发期间取回，零弹炮台回到队列

- 位置：`scripts/app/game_controller.gd:215` 的 `return_turret`；`:375` 的 `_settle_ticket`。
- 路径：最后一发扣到 0 → DRAINING → 玩家点取回改为 RETURN_PENDING → 命中结算跳过仅针对 DRAINING 的删除 → `_settle_return_pending` 把零弹炮推回列首。
- 后果：再次上位不能开火，又不自动消失；可以持续占槽或堵列首。
- 修复方向：结算优先依据 ammo_remaining==0 且 in_flight==0 清理耗尽炮台，再处理有弹取回；不要仅靠互斥状态字符串判断耗尽事实。
- 验收：剩余一发时点取回，分别命中、错撞返还、超时返还、保存取消；成功命中删除炮台，取消返还后回列首一发，每色守恒且所有权唯一。

### R02 / P1：持久化测试会覆盖并删除正常游戏存档

- 位置：`tests/persistence/test_persistence.gd:54` 附近的 `repo.save(a.to_snapshot())` 及末尾 `delete_save`。
- 测试用正式 level_01/level_02 和正式 `user://saves`，未隔离目录或恢复原文件。
- 后果：同一用户数据目录下运行测试，覆盖真实进度，测试完成还会删除存档。
- 修复方向：仓库路径可注入，测试使用独立临时目录；测试失败/中断也不能触碰真实档。
- 验收：预置真实存档，测试成功及中断后哈希都不变。本轮未执行此测试。

### R03 / P2：触摸释放事件被当成按下重新占有

- 位置：`scripts/app/main.gd` 的 `_unhandled_input`（复读时约第 167 行）。
- `_input` 在抬手时 release；随后未被 UI 消费的同一 ScreenTouch 进入 `_unhandled_input`，无 pressed 判断就 press。
- 后果：抬手后 active pointer 残留，多指切换时另一个触点可能被忽略。
- 修复方向：触摸按下分支判断 pressed；释放统一处理，不重复认领。
- 验收：单指抬起后 owner 清空；手指 A 抬起后 B 可旋转；UI 按下后移出抬起不产生模型手势；失焦恢复正常。

### R04 / P2：结束的物理球记录不回收

- 位置：`scripts/projectile/projectile_system.gd:48`、`:56`、`:70`。
- `_balls` 只追加，结束只设 active=false；每帧 step 和 active_count 遍历历史全部记录。
- 后果：4105 块至少积累数千记录，返还重射使记录更多；性能随累计发射量恶化，不随当前活跃球数量保持稳定。
- 修复方向：完成本步 hit/ended 事件快照派发后回收；需要诊断时只保留有界历史。不能在 BallPhysics 读取快照前删除。
- 验收：连续发射/返还后数据容器大小约等于活跃数加有界历史；全清后无残留活跃球；重复结束仍安全。

### R05 / P2：无可变排列的随机排仍扣次数

- 位置：`scripts/gameplay/cannon_queue_service.gd:129` 的 `shuffle_columns`。
- 总炮数>=2 即允许，但只列内洗牌；五列各一门时没有任何交换仍返回 true。
- 修复方向：按实际重排规则判断变化空间。若设计允许跨列，需明确长度和 origin_column 语义后统一实现；若仅列内，至少一列>=2 才存在交换空间。
- 验收：全空、单炮、多列单炮、单列多炮；无变化空间不扣库存、数据不变。

### R06 / P2：initial_slots 配置未应用到新会话

- 位置：`scripts/data/game_rules.gd:28` 读取配置；`scripts/level/level_session.gd:18` 默认 3；`GameController.start_level` 新局初始化。
- 后果：设置为 2 或 4 仍以 3 开局，关卡条件与配置不一致。
- 修复方向：校验范围后用 rules.initial_slots 初始化 unlocked_slots；恢复时单独校验保存值，不覆盖合法进度。
- 验收：不同初始值的槽位显示、leftmost_free、满槽拒绝一致；非法值加载失败。

### R07 / P2，S09 未完成：存档没有模型兼容与结构完整性验证

- 位置：`scripts/level/level_session.gd:26` 的 `to_snapshot`、`:45` 的 `restore`；`GameController.start_level`。
- 当前只核对 version/level_id；不含 model_revision/hash、规则版本、RNG state。restore 直接访问嵌套字段，未验证五列/五槽、ID 引用唯一、合法颜色、活体素范围、弹量及守恒。
- 后果：同关模型改版后旧体素 ID 被套到新模型；JSON 合法但结构损坏的档案可能触发运行错误或产生重复归属。随机种子字段也没有恢复到实际 `_rng`，不能保证继续后的随机序列一致。
- 修复方向：先在临时结构完整校验，再原子提交；模型不兼容备份并明确提示重开，禁止靠替换无效炮色伪装修复。恢复 RNG 的实际 state；保存/恢复错误要传到 UI。
- 验收：v1、同版本模型变更、缺字段、重复 ID、错误列长、非法存活 ID、负弹量、在途保存、坏档均覆盖；拒绝后不破坏当前会话及原存档。

### R08 / P2，S08 未完成：任意指扣次无效果，待发道具可重复扣次

- any_color 标记没有目标选择或发射消费路径。speed_x2 已待发时再次点击，仍扣库存但只保留一个 true。
- 修复方向：接通指定目标模式；待发期间禁用重复激活，或明确定义可保存多个次数的队列，不采用重复扣次但不累积的现状。
- 验收：成功激活一次、重复点击、无合法目标、目标失效、两个炮同时发射时仅一个成功发射消费一次效果。

### 6.1 性能优化要针对实际热点

1. **先控制对象数量**：回收物理球、限制飘字/光圈、保留现有球视图池；全局事件去重表也应随会话有明确寿命。
2. **目标候选去重**：`TargetSelector.on_voxel_destroyed` 会把邻居重复 append，查询只去死块不去重复。改成集合或带成员标记的前沿，避免同一存活候选重复 DDA/扫掠。
3. **目标查询设预算**：当前多炮冷却到期可在同一帧集中搜索。按旋转版本、体素变化版本使等待结果失效，配合低频重试与每帧查询预算，避免无目标时每炮反复全查。
4. **HUD 合并刷新**：现在多个事件都立即 refresh 全部槽/列/道具；一发命中可能触发多次完整刷新。事件标脏后每渲染帧合并一次，或只刷新受影响项。
5. **测量再决定复杂化**：保留单 MultiMesh 与空间索引，不先重写 ECS、增加线程或上逐块物理。先分别测目标查询、碰撞、UI 和效果开销。

### 6.2 必须补的验收场景

- 最后一发：正常命中、取回中命中、超时返还、保存返还，各自检查炮台去留和弹量。
- 多炮：同帧争同一目标、目标已预订、旋转造成遮挡、各炮独立结算，不重复删块。
- 队列：后排不可直接上位、滚动不旋转、满槽不出列、零弹不回列、合成失败无半事务。
- 道具：待发重复点击、无目标、目标消失、同时开火唯一消费、满槽加槽拒绝。
- 存档：坏 JSON 与结构坏档分别测；模型更新、后台强制结束、返回再进入；原档可恢复。
- 多分辨率：1080×1920（竖屏16:9）、1080×2340（19.5:9）、1080×2400（20:9），包含安全区。历史 frame_probe 的宽屏尺寸记录不能代替竖屏16:9验证。
- 性能：真实4105块、五槽可用测试场景、最大效果预算；至少120s有效采样，沿用任务阈值稳态>=30 FPS、p95<=50ms、内存峰值<=512MB、预热后60s增长<=10%。必须注明设备、渲染方式和日志开关；用平台进程指标补充静态内存统计。
- 稳定性：30轮进关/发射/返回/重开，以及至少一轮完整通关；生命周期循环不能冒充30次通关。

## 7. 交付时如何判断“接近参考图”

建议固定三个可复现检查点，分别对应本轮三张参考图的用途：

1. **开局静态**：默认角度，完整模型、剩余4105、空槽、前三排队列、四道具、暂停入口全部可辨。比较构图和信息层级，不要求照抄4577或关卡7。
2. **双炮消除**：两个可发射炮位、旋转后的模型、可见弹珠/拖尾/碎块/光圈、连击。记录当时实际剩余数，不伪造与参考图一致的数值。
3. **中期剥层**：记录累计消除量和当前朝向，展示内部颜色、空缺形状、下一排炮台以及取回/换炮策略。证明旋转和队列选择有意义，避免长时间只有单色等待。

每个检查点附同一构建的截图、短视频、模型 hash 和状态日志。视觉验收与逻辑验收分开：截图好看不能证明守恒，测试全绿也不能证明按钮够大、碎片可见、操作顺手。
