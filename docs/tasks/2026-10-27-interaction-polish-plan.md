# 旋转手感、炮台上位退场与可见目标响应优化方案

日期：2026-10-27（Asia/Shanghai）。本轮只读核查当前工作区并新增技术文档，不修改代码、不启动游戏。当前源码有大量未提交改动；Claude 实施前必须重新核对，保留已有成果。

## 1. 上下文与目标

现有游戏已实现局部空间弹道、多球连发、8°/s自动旋转、拖动接续、三排队列、合成、指定目标、暂停与Mac App回放。已有报告记录约211～237秒全清，但不能据此认定所有人工操作边界通过。

本轮用户反馈：

1. 左右、上下拖动青蛙手感别扭。
2. 炮台上位像卡一下后瞬移，移动过程不连续。
3. 弹药耗尽后炮台突然消失，需要退场动画。
4. 肉眼看见同色块，炮台却不发射，需要提高可见目标响应。

保持：macOS图形App验收、同色消除、一发一块、真实碰撞、分色弹量守恒、旋转中命中、正常操作有效局时<=300秒。**取回按用户最新要求保留用于测试，不删除。** 使用取回的调试记录与无取回正式通关证据分开。旧方案要求删除取回的段落在本轮不执行。

本文涉及旋转控制和动画时序时优先于旧方案；已实现的功能只做必要适配，不重新搭建。

## 2. 核查到的具体原因

| 问题 | 当前证据 | 影响 |
|---|---|---|
| 侧面上下拖动可倒立 | main._apply_rotation绕屏幕X/Y轴叠加；用模型前向向量与up的夹角限俯仰 | 侧面前向接近X轴时，绕X旋转并不改变该夹角，限位失效 |
| 交替拖动越转越歪 | 两个三维增量不断左乘当前Basis，没有独立yaw/pitch和侧倾约束 | 右下左上等幅拖动可积累侧倾；不是单纯灵敏度问题 |
| 边界拖动被吞 | 越限就舍弃本次整段pitch增量 | 到边界突然不动，斜拖只剩横向 |
| 两套角度不一致 | GestureRouter对内部_pitch钳制，但返回原始增量；显示姿态另行累计 | 测试读出的角度不能代表实际模型朝向 |
| 上位看似瞬移 | place_front立即READY并注册射击；HUD立即refresh目标槽；另建只有TEX_BODY的ghost飞0.18s并淡至0.3 | 槽内完整炮台已出现甚至开火，飞行残影不再被看作同一门炮 |
| 到位弹跳时机错误 | _play_place_animation启动时立即调用槽位place_feedback | 炮台还没“飞到”，目标槽已弹跳 |
| 耗尽无动画 | _settle_ticket删除turret并slots_changed；refresh直接设empty | 整门炮瞬间消失 |
| 暴露边角漏选 | TargetSelector用positions[id]+(0.5,0.5,0.5)作为唯一瞄点 | 中心射线被挡但外侧面可达的块不被选中 |
| 旧原点结果直接发射 | 分片扫描锚定origin0，成功返回后_fire_at用当前origin_grid，没有最终实时复核 | 旋转中旧原点可达不代表新原点可达 |
| 粗格负缓存过时 | 负缓存仅匹配color/量化origin/gen，忽略小幅旋转与真实原点变化 | 同格内新出现可达目标仍可能等待；停止拖动后不一定自行恢复 |

旋转公式的独立数值复算显示：侧面朝向持续下拖180°，模型up变为(0,-1,0)，现有tilt判据仍为0°；四次右/下/左/上各30°后，up约为(-0.25,0.967,-0.058)。这是公式层证据，不是本轮实际App录屏复现。

## 3. 旋转：改成稳定的两轴模型查看控制

### 3.1 一个姿态来源

使用独立yaw、pitch状态，禁止将每次自由旋转直接累乘到任意Basis。GestureRouter只提供已归属指针的位移/按下释放，不再维护另一套假权威角度。

推荐相机坐标系中的显示姿态：`B = C × Rx(pitch) × Ry(yaw) × B0`。C为固定展示相机朝向；B0为确认模型初始正面和直立方向的固定校准。相机不跟着输入旋转，UI保持固定。每步由yaw/pitch重建姿态并走唯一set_orientation入口，维持原点和体素变换契约。

这个顺序保证模型竖直轴的屏幕水平分量不随yaw积累侧倾；上下拖调屏幕横轴俯仰，左右拖改变转台方位。不能改成自由滚动球控制，也不能把顺序随意交换后沿用同一验收结论。

**设计取舍要明确**：手动俯仰后，Rx外层使yaw轴相应倾斜；因此“自动旋转始终绕固定世界+Y”的旧实现约束在这个控制方案下放宽为“沿同一yaw轴慢速连续逆时针，保持当前pitch”。pitch=0时仍等价固定竖直轴水平转台。这样才能保证松手接续不重新把姿态扭歪。它是本轮为改善手感提出的实现决定，不冒称用户指定了矩阵顺序。不要同时执行旧世界Y增量和新yaw累计。

### 3.2 输入与边界

- yaw可连续跨360°，归一化仅为数值稳定，不在跨界时插值绕远路。
- pitch先建议限制±60°，作为可调手感值；计算 `pitch=clamp(pitch+delta)`，超出部分才丢弃。反向拖动立即离开边界。
- 左右/上下各自配置灵敏度，按模型交互区域的逻辑尺寸归一化；初始候选为横扫区域宽度转180°、纵扫区域高度覆盖120°，在实际Mac窗口调试，不以物理屏像素混算。
- 先做无惯性、无明显输入延迟版本，不先叠加弹簧或长时间平滑掩盖错误。若加入轻微滤波，记录延迟且不造成松手漂移。
- 在yaw=0/90/180/270°以及pitch边界检查当前可见表面随手方向；方向符号不能只用初始瞳孔标记判断。
- 已接受模型按下立即hold自动旋转，只有该指针释放才能解除；拖动中不叠加自动yaw。松手从当前yaw/pitch继续8°/s，可保留0.2s渐入，不补转拖动时间。
- 输入意图在同一物理步统一应用，随后选靶和局部球推进；不让渲染帧和物理帧分别写不同Basis。暂停/选择目标/失焦按既定规则处理。
- 旧存档没有姿态时用默认姿态；若新保存角度，只存规范yaw/pitch，不恢复任意含侧倾Basis。切局重置手势和滤波状态。

## 4. 上位：完整炮台移动，到位再开火

### 4.1 状态和时间

建议新增真正有效的LOADING阶段，而不是立即READY。点击验证成功后原子出列、占槽、登记turret_id/generation/transition_id；该槽不可再次占用，炮台归属只有一份。

建议总时长0.28秒：移动约0.24秒，轻微到位压缩/回弹约0.04～0.08秒（可以重叠）。这些是调优起点，不是硬编码的用户要求。至少一个渲染帧内给出按压反馈，避免搜索重活阻塞动画首帧。

控制器用可暂停的模拟时钟管理loading_remaining；到零切READY并注册调度。**不依赖Tween完成回调作为唯一业务推进入口**，避免窗口隐藏、动画被杀、headless运行时永远卡在LOADING。表现层读同一开始时间/时长推进进度；不能使用彼此独立的两个计时器逐渐错位。

### 4.2 画面组织

1. 数据修改前捕获列首屏幕矩形和完整炮台视觉快照：底座、炮身、炮管、数字、颜色及朝向。
2. 在不受队列裁剪的顶层过渡层显示完整移动炮台，不再只用TEX_BODY残影；位置和尺寸从源矩形平滑过渡到目标矩形，主体保持清晰不半途淡没。
3. LOADING时目标槽只显示底座/落点提示，不再立即画第二门完整炮台。源对象已出列，后排从旧位置向前补位。
4. 移动结束再播放落位反馈，完成视觉接棒后移除过渡对象，目标炮台开始开火。若一帧内跨过完成时刻，仍不得出现重复炮、闪空或从错误炮口发射。
5. 同列连续操作建议在短暂上位动画期间阻止该列二次点击并给出状态，其他列可并行；不要通过吞点击造成无反馈。补位Tween以列为单位管理，避免多个Tween争写_col_shift。
6. 布局变化时重算目标矩形但保持当前插值进度；refresh不得销毁/覆盖过渡所有权。所有动画由generation+transition_id校验，旧回调不能碰新关卡。

### 4.3 取回、保存、暂停

测试取回LOADING炮台时，最简单安全规则是短暂拒绝并提示“上位中”，到位后可取回，不新造复杂反向动画。暂停冻结逻辑和画面在同一进度；重开/返回清理过渡层。保存时把LOADING归一为READY并明确恢复时不重播，或保存剩余时长，两者选定一种贯穿测试；禁止恢复后卡住或重复出列。

## 5. 耗尽：等在途结算，再自然退场

状态路径建议：READY/FIRING → DRAINING（弹量0但在途>0）→ RETIRING（弹量0且在途=0）→ 删除并释放槽位。

- DRAINING保持炮台，数字可显示0和“结算中”视觉，不立刻播放消失；返还弹量时恢复READY/FIRING，不能先销毁再补一门。
- RETIRING建议0.20秒：小幅收缩至约0.15倍并淡出，可加少量无物理碎光；原地收起，避免大爆炸遮挡模型。
- 保留槽位预留直到短暂退场完成，保证下一门不能与旧炮重叠；退场进度由模拟时钟保证完成，Tween只表现。等待释放时点击反馈明确，不能额外扣弹或丢队列元素。
- 收尾条件优先依据ammo/in_flight真实数值，不能只看DRAINING字符串：RETURN_PENDING可能覆盖状态。测试取回最终结算为零弹时，应进入退场并删除，不能回队列。
- retire_started携带不可变视觉快照，随后refresh能区分RETIRING而非立刻empty；新增事件同步白名单和订阅，不复用含糊的销毁通知。
- 保存前可原子完成RETIRING并释放零弹炮，恢复不出现幽灵槽；重开/返回取消旧视觉对象。所有路径保证唯一归属和计数不负。
- 最后一块消除后先停止新射击，允许已开始的退场在短暂结算过渡中播完，再显示胜利遮罩；不要因outcome停止step而把RETIRING永久冻结。终局视觉过渡用独立、有界、可取消的清理流程，不能重新推进玩法。300秒记录包含最终可见结算，不能藏掉这段时间。

## 6. 可见同色目标：暴露面多点扫描与及时响应

### 6.1 不把视觉可见等同于炮口可达

相机与炮口不同位置，肉眼可见不一定可从该炮口到达。先解决中心瞄点太苛刻、缓存过时和旧原点复用，不能直接允许穿异色、隔块删除或扩大到无条件命中。

保留原球半径；不要先缩小物理球而显示大球，也不要直接删掉挡路块。若多点扫描后仍经常出现视觉可见但不可达，再用真实轨迹记录决定是否另设绕行规则，本轮不默认加入绕障寻路。

### 6.2 目标契约升级

TargetSelector成功结果需包含 `{voxel_id, aim_grid_point, face_id, origin_used, geometry_version}`。控制器不能拿到结果后再次把瞄点换回体素中心；球方向、炮管、预订和发射快照都使用同一个aim_grid_point。

候选生成复用已有暴露面掩码：

1. 先试旧热点和中心，保持常见场景成本低。
2. 中心失败后，对朝向炮口的暴露面依次尝试面中心及向四个角内缩的采样点；例如每面5点，面内坐标取0.2/0.8作为首轮候选，避免恰好在数学边缘。最多6面×5点，实际先筛面并分片。
3. aim点位于该面略向块内偏移的位置，足以让扫掠穿过目标扩张盒表面；偏移量按格尺寸给出，不能停在浮点边界导致无hit。
4. 每个点都以真实球半径对全部候选做连续扫掠，只有first_hit==目标且同色才接受。没有合法点时不发射。
5. 改造中心专用的DDA预过滤：面点射线落格与中心不同，预过滤不能把目标自身或边界相邻格误当遮挡；用完整扫掠作为正确性基准建立夹具。
6. 采样优先级考虑当前炮口距离/面朝向/已有命中热点，预算用尽下帧继续；全局预算覆盖所有炮、所有点和候选构建，避免每炮各拿3ms叠加。

### 6.3 缓存与最终复核

- 量化原点只能索引候选提示，不能永久代表该格内所有原点都无目标。完整否定结果须带精确几何版本，或仅做有明确上限的短暂退避（建议<=100ms），原点/旋转/体素/预订变化触发重查。
- 持续自动旋转时保留公平候选/采样游标，但实际候选按当前原点检查；跨不同原点扫完一圈不能生成严格否定证明。不要因每步版本变动就从头扫，使后段永远得不到时间。
- 分片返回的成功目标，在提交预订和扣弹前，必须从本次真实炮口对aim_grid_point最终复核。失败则继续找目标，不扣弹、不播放开火；不能用origin0的旧结果生成当前原点弹道。
- 预订全部占满与被遮挡分开处理：前者由命中/取消释放唤醒；后者随旋转重查；scan_pending不能统一等待一个完整射击冷却周期。
- 诊断面板显示等待原因、目标ID、采样点、搜索耗时/等待时长、预订数、最后取消原因；普通HUD只给简短提示，不展示实现参数。
- 为避免指定目标选择被其他炮抢先消费，沿用独占预订规则；多点确认接口同时用于指定目标与普通自动选靶，不能两套标准不一致。
