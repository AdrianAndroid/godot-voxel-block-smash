# 第 1 章：先理解编辑器在管理什么

[总目录](README.md) · [下一章](02-project-and-rules.md)

## 本章目标

这一章不要求你会三维数学，也不要求你马上看懂上千行控制器。完成之后，你应当能启动一个独立练习工程，添加一个按钮，点击时在输出面板看到消息，并解释脚本为什么能够收到这个消息。这个小闭环对应整个游戏的缩小版本：接收意图、改变状态、反馈结果。以后按钮换成炮台、输出换成模型消除，控制关系仍然成立。

先按总目录创建练习副本。不要把正式游戏的主场景直接改成实验场景；学习中最常见的挫败不是语法不会，而是为验证一个小概念破坏了原先能运行的系统。独立练习工程让每次错误都有有限的影响范围，也让“这是我刚才的实验”与“这是项目已有实现”保持清楚。

## 概念讲解：对象、树和保存文件

节点（Node）是参与场景树的对象。普通 Node 可以组织生命周期，Node3D 增加三维变换，Control 用于界面布局。它们不是三种不同语言，而是不同能力的基类。选择节点类型时应问：我需要它参与哪一种引擎服务？纯粹计算一个合成结果并不需要屏幕坐标，也不需要每帧回调，因此项目中的不少服务继承 RefCounted，而不是 Node。

场景（Scene）是可保存、可重复实例化的一棵节点树。`.tscn` 文件描述节点关系、资源引用和属性值，运行时才创建真正的对象。可以把它理解为对象装配说明，而不是已经运行的对象。保存一个炮台场景后创建五个实例，得到五个独立节点实例，但它们可能共享同一份纹理或网格资源。这个区别以后会直接影响内存和材质修改行为。

脚本（Script）扩展某个对象的行为。`extends Node3D` 表示脚本实例具有 Node3D 的能力；它不是把一个函数文本简单塞进现成节点。脚本上的 `_ready()` 在节点及其子节点准备完成时运行，适合取得子节点和连接事件。`_process(delta)` 按渲染循环调用，`_physics_process(delta)` 按物理步调用。先记住调用语义，暂时不要把所有工作都写进这两个循环。

信号（Signal）表达“某件事发生了”，接收方自行决定如何反应。Button 的 `pressed` 不需要知道接收方要启动关卡还是播放声音。这种解耦能让同一个发射事实同时触发音效、炮口反馈和统计。项目还实现了自定义事件总线，它与引擎信号是不同层次的机制，不能看到“事件”两个字就当作 Autoload。官方的 [信号入门](https://docs.godotengine.org/en/stable/getting_started/step_by_step/signals.html) 可以补充编辑器连接流程。

| 术语 | 在本项目中如何理解 |
|---|---|
| GDScript | 编写逻辑的语言，缩进形成代码块，类型注解帮助提前发现错误 |
| Node / 节点 | 挂入场景树、可以接收引擎生命周期的对象 |
| Scene / 场景 | 节点树的可复用保存形式，运行时实例化 |
| Resource / 资源 | 可被对象引用的数据，例如网格、材质、纹理 |
| Signal / 信号 | 发出通知，由连接的接收方处理 |
| Autoload / 自动加载 | 引擎启动时加载的全局对象机制，本项目的会话总线不依赖它 |
| RefCounted | 按引用计数管理生命期的对象，适合纯逻辑服务 |
| SceneTree | 运行场景的树与循环入口，测试脚本可直接继承它 |
| res:// | 当前工程根目录内的资源路径 |
| user:// | 当前应用的可写用户数据目录，不等于工程目录 |

## 动手步骤：建立一个只做一件事的场景

在终端执行下面的准备命令，它只在练习副本创建最小工程。这里有意不复制正式主场景，避免新手一启动就面对大量动态装配。项目配置文件只写名称和渲染器，其他设置留给下一章逐步加入。

```bash
mkdir -p "$TUTORIAL_LAB/sandbox"
cat > "$TUTORIAL_LAB/sandbox/project.godot" <<'EOF'
config_version=5
[application]
config/name="Voxel Tutorial Sandbox"
[rendering]
renderer/rendering_method="gl_compatibility"
EOF
"$GODOT_BIN" --editor --path "$TUTORIAL_LAB/sandbox"
```

编辑器中选择新建“用户界面”场景，将根 Control 改名为 `HelloUI`。保存为 `hello.tscn`。在根下添加 Button，命名 `StartButton`，检查器把 Text 设置为“试一下”。选中按钮，用布局工具给它一个可见位置和足够大小。根节点挂接脚本 `hello.gd`，填写以下教学简化版。这段代码不是游戏已有文件，完整游戏装配入口见 [scripts/app/main.gd:30](/Users/zhaojian/code/godot-voxel-block-smash/docs/tutorial/source-baseline/scripts/app/main.gd.txt:30)（[GitHub 源码](https://github.com/AdrianAndroid/godot-voxel-block-smash/blob/003648e3ac102692c9722b441ba2f801c2f6ac1d/scripts/app/main.gd#L30) · [仓库内快照](source-baseline/scripts/app/main.gd.txt)）。

```gdscript
extends Control

func _ready() -> void:
    # 子节点已经就绪，名称必须与场景树一致。
    $StartButton.pressed.connect(_on_start_pressed)

func _on_start_pressed() -> void:
    print("按钮收到点击，场景连接正常")
```

使用编辑器“运行当前场景”，而不是先运行整个项目。点击按钮，观察输出。然后把按钮文字改掉再运行，确认你知道“属性修改”和“脚本行为修改”的差别。最后把节点临时改名为 `LaunchButton`，保留脚本原路径，观察报错，再把名字恢复。这个有意制造的错误说明 `$StartButton` 实际是一条节点查询，而不是根据按钮文字模糊寻找控件。

认识五个面板时，以刚才的操作为线索：场景面板回答“对象如何嵌套”；文件系统回答“哪些资源已保存”；检查器回答“当前对象属性是什么”；节点面板提供信号等连接入口；输出与调试器回答“运行时到底发生了什么”。只在文件系统看见 `.gd`，不能证明它已经挂在节点上；检查器看见脚本路径，也不能证明该节点已进入当前运行的树。

现在预览正式主场景 [scenes/main/main.tscn:12](/Users/zhaojian/code/godot-voxel-block-smash/docs/tutorial/source-baseline/scenes/main/main.tscn.txt:12)（[GitHub 源码](https://github.com/AdrianAndroid/godot-voxel-block-smash/blob/003648e3ac102692c9722b441ba2f801c2f6ac1d/scenes/main/main.tscn#L12) · [仓库内快照](source-baseline/scenes/main/main.tscn.txt)）。文件里只有 Main、Camera3D、DirectionalLight3D、WorldEnvironment 等基础节点，并没有你截图里看到的全部按钮。原因是 `main.gd` 在运行时创建控制器、表现节点和 CanvasLayer。以后调试这种工程，要切到运行时 Remote 场景树查看实际对象，不能仅凭编辑器静态树判断“HUD 丢了”。

> 📷 截图：HelloUI 场景树、Button 检查器与输出消息；建议在独立 sandbox 实验中自行截取。正式树可用运行时 Remote 面板截图。

### 延伸练习：把对象生命周期真正看见

给 HelloUI 的 `_ready()` 加一条输出，再给按钮回调加一个点击计数。启动一次、点击三次，你应看到一次准备消息和三次点击消息。关闭再启动，局部计数重新开始。这个实验让“对象创建一次”和“事件发生多次”的区别可见。若每次点击都创建新按钮，你会看到场景树增加；若只是改变按钮文字，对象数量不会变化。以后排查球对象增长，就沿用同样观察方法。

再思考资源共享。五门炮可以共享同一张炮身纹理，但每门炮的弹药数字必须不同。纹理是共享资源，数字是实例状态。若你把一个共享材质整体改成红色，其他使用者也可能受影响；若只改某个节点的显示属性，影响范围则更小。不要背“资源永远共享”这种绝对规则，而应检查它是同一个引用还是复制出来的对象。

练习阅读报错时，从第一条错误开始。后面的空引用可能只是前面节点没创建成功的连锁结果。把第一条报错的文件、行号、调用时机记下来，先修一个原因再重新运行。这个习惯会显著减少用AI排错时的无效往返：提供最小现场，比只说“运行不了”更容易得到可验证的修复。

## 踩坑记录：从入门错误连接到真实工程

新手常把“脚本存在”“节点实例存在”“节点正在运行”混成一个状态。项目中特别值得留意的反例是旧 App 实例：UX 历史报告记录过一个长时间闲置的旧进程仍写性能文件，导致观察者把旧窗口当成新构建。技术原因不是按钮没保存，而是你正在观察另一个运行实例。以后每次测试，应知道启动了哪一个路径、哪一个进程、哪一个关卡。

另一个误区是信号连得越多越保险。对同一会话反复绑定表现层却不清理旧订阅，会让一次命中播放两次效果，甚至让旧场景响应新关卡。当前控制器在 `start_level` 中建立新的会话总线，体现的是生命周期边界，不是“每次都 new 更安全”的通用规则。哪些对象能跨局共享，哪些必须重建，应当根据它们是否携带局内状态来判断。

不要为了调用一个工具函数把整个场景树变成全局单例。资源加载器、颜色统计和碰撞求解可以独立测试，正是因为它们不依赖按钮是否显示。你先用简单信号理解对象通信，再看自定义总线携带关卡、代际和事件标识，就能理解工程复杂度来自真实约束，而不是“做游戏必须写很多架构”。

## 验证方法

依次检查三件事：按钮可见；一次点击只输出一次；节点名与脚本路径不一致时能定位到出错行。将“运行当前场景”和“运行主场景”各试一次，解释它们为什么可能显示不同内容。若只能在编辑器预览看见按钮，运行后看不见，先检查运行入口和布局，而不是重装引擎。

本章完成后你应该能看到一个可点击按钮，并能画出 `HelloUI → StartButton` 的对象关系。进一步用自己的话解释：按钮发出 `pressed`，根脚本接收，输出系统显示文字。后面的炮台发射链路会更长，但每一段都应有同样清楚的输入、处理者和输出。

## 小结

本章的产物不是游戏功能，而是观察运行系统的方法。以后每遇到异常，先确定对象是否被创建、是否进入正确的树、是否收到输入、事件是否只有一份。带着这个顺序进入第二章，配置文件就不再是一堆需要照抄的陌生键名。
